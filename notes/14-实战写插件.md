# 第14篇：动手写一个插件，让模型用上你的工具

前面十三篇都在拆别人的代码。这一篇换个方向：写自己的。

目标很小——做一个能让模型调用的工具，叫它 `greet`，模型传一个名字进来，它回一句问候。听起来没什么用，但它是所有工具的骨架。骨架通了，后面加什么都行。

## 一、一个插件就是一个文件

先看完整代码，就这么多：

```ts
import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'greet-tool'
export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.tools.register(defineTool({
    name: 'greet',
    description: 'Greet the named person.',
    parameters: {
      name: { type: 'string', required: true, description: 'Who to greet' },
    },
    output: {
      schema: { type: 'string' },
      render: (_args, value) => [{ type: 'text', text: value }],
    },
    async execute(args) {
      return `Hello, ${args.name}!`
    },
  }))
}
```

三行声明，一个函数。我们逐行拆。

**第一行 `export const name`**：这个插件叫什么。出错时日志里显示它，排查靠它。

**第二行 `export const inject = ['tools']`**：我依赖"工具注册表"这个服务。这句话不是注释，是加载器要看的——它会等这个服务就绪，才调你的 `apply`。这就是第03篇讲的"顺序由依赖决定"。

**第三行 `export function apply(ctx)`**：插件主体。所有注册都发生在这里，所有注册都会在插件卸载时自动撤销。

## 二、defineTool 里的四个字段，各管一件事

`defineTool` 收的四个字段，其实对应四个不同的问题：

**`name`**——模型眼里的工具名。要短、要像一个动作，别起 `my_super_helper_v2` 这种。

**`description`**——模型判断"什么时候该用我"的唯一依据。这一句写得含糊，模型就不用你。写清楚"干什么"和"什么时候干"。

举个反例：`description: '处理文件'`。模型看到这句，既不知道自己该用它、还是用现成的读文件工具，也不会知道它能不能读二进制。结果就是两种：要么永远不用，要么用错地方。写成"读取文本文件并返回前 N 行，二进制文件会报错"，判断依据就有了。

**`parameters`**——模型填参数用的表格。你写 `{ type: 'string', required: true }`，模型看到的是一份 JSON Schema，知道这个字段必填、是字符串。`args` 的类型也是从这里推出来的，写错编译就报。

**`output`**——返回值长什么样。这一项最容易被跳过，但它很关键，下一节单说。

## 三、execute 拿到的是已经洗干净的数据

有个细节值得停一下：**你不用自己校验参数**。

模型返回的 `arguments` 是一段字符串，可能字段缺失、类型不对、多塞了东西。这些校验在 `execute` 之前就做完了——必填键、类型、字面量约束、联合分支，都按你的 schema 查一遍。进到 `execute` 里的 `args`，已经是类型正确的对象。

那你还要查什么？schema 表达不了的东西：非空字符串、正数、两个字段之间的相互约束。这些得自己判断。

还有个约束容易被忽视：**`args` 当只读用**。注册表把这份参数冻结了，你要加工就自己复制一份。

## 四、返回值分两层：给程序的值和给人的话

这是新手最容易做拧的地方。

很多工具直接 `return "操作成功，文件已写入 /tmp/a.txt"`——一句话里混了三件事：成功没成功、写到哪、给谁看。调用方要拿路径，只能从这句话里抠字符串。

dsh 的做法是拆成两层：

**第一层是规范值**。`execute` 只返回结构化数据，比如 `{ ok: true, path: '/tmp/a.txt' }`。程序之间传的是这个，不解析自然语言。

**第二层是渲染**。`output.render` 把这份值变成人（和模型）看的内容块。想显示成一行字就显示一行字，想显示成一张卡片就生成卡片数据。

同一个值，可以有两种呈现——这跟第10篇讲的"模型看 schema、人看卡片"是同一套思路，往下一层延伸了一步。

还有个细节：**抛异常就等于失败**。工具里出基础设施故障（文件读不到、网络断了），抛出去就好，注册表会接住并标成错误。而"业务上不理想但执行成功"的情况（比如命令跑完退出码是 1），应该老老实实写进规范值，让渲染层去解释——不要用抛异常来表示业务状态。

## 五、注册是副作用，卸载自动收回

`ctx.tools.register(...)` 返回的东西挂在当前插件身上。插件被卸载，工具就从注册表里消失。

这条规矩看着平淡，实际决定了热重载能不能用：你改了工具定义，插件重建，旧工具跟着走，新工具顶上。不用手写清理逻辑，也不会出现"同一个工具注册了两遍"。

但要记住一句话：**注册后不要再改那份定义**。schema 和回调被借用了，不是复制过去的。想换实现，就卸载旧的、注册新的。

## 六、装进去：只在配置里加一行

插件写完了，怎么让它跑起来？不用改启动代码，在组合清单里加一行：

```yaml
- name: '@deepseek-ai/dsh-system-prompt'
- name: '@deepseek-ai/dsh-tools'
- name: './greet-tool.ts'
```

注意 `dsh-tools` 前面还有一行 `dsh-system-prompt`。原因很实在：工具要把自己的 schema 贡献给系统提示词，所以它依赖提示词服务。清单里少写这一行，你的插件会一直停在 PENDING——第03篇说过，等一个永远不会出现的服务，就是"写了没反应"的头号原因。

排查时按这个顺序走：先看有没有 PENDING，有就查 `inject` 里列的服务在不在清单里；再看 `apply` 有没有被调用，没调用说明依赖还没满足；最后看 `apply` 里抛没抛异常，抛了会进 FAILED。三步之内基本能定位。

真跑起来，控制台会打印：

```
[tool-logger] greet -> Hello, Cordis!
```

（`tool-logger` 是下面那个旁观插件，先卖个关子。）

## 七、再写一个旁观者，验证插件之间真的互不认识

只测自己不算数。再写一个插件，专门盯着"每次工具调用结束"这个时刻：

```ts
export const name = 'tool-logger'
export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.on('tools/result', (exec, result) => {
    console.log(`[tool-logger] ${exec.name} -> ...`)
  })
}
```

它不知道 `greet` 的存在，`greet` 也不知道它的存在。两者只通过两样东西连上：注册表服务，和事件。

这就是第03篇那句"一切皆插件"落到实处后的样子：加一个功能，不用通知任何人，只要挂在约定的事件或服务上。

## 八、从这个小工具走到一个完整 agent

一个真实 agent 是什么？就是这套组合再堆一批插件：模型适配器、agent 循环、会话持久化、工具执行器、权限与沙箱、界面。

所以第09篇那份几百行的 `cordis.patch.yml`，你现在可以一行行读下去了——里面没有魔法，就是这份清单的加长版。
