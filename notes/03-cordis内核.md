# 第03篇：Cordis 内核，插件到底是怎么被加载的

前两篇我们反复说一句话：dsh 没有内核，一切皆插件。

那问题来了——既然什么都是插件，谁来加载插件？答案是一个叫 **Cordis** 的东西。dsh 把它以 vendor 的方式（源码直接拷进来，不发版）放进仓库，自己不重复造这个轮子。

这一篇我们就钻进 Cordis，看清楚三件事：一个插件长什么样、它按什么顺序被加载、插件被卸载时会发生什么。材料全部来自上游 `docs/cordis-primer.zh.md` 和 `docs/cordis-tutorial/`。

## 一、一个插件，长什么样

Cordis 里最常见的插件，就是一个导出了 `apply` 函数的文件：

```ts
export const name = 'hello'
export function apply(ctx: Context) {
  console.log('hello from my first plugin')
}
```

启动器创建一个根上下文 `ctx`，Loader 插件读一份 `cordis.yml` 配置，然后一个一个把里面列的模块挂载进来，调用它们的 `apply(ctx)`。插件通过 `ctx` 注册自己贡献的一切——一个工具、一段提示词、一个监听器、一个服务。

Cordis 一共接受三种插件形态：

1. **函数插件**：上面这种，最常见，不需要 `apply` 方法，Cordis 直接调函数。
2. **对象插件**：一个带 `apply(ctx)` 方法的对象，可以附自己的元数据。
3. **类插件**：继承 `Service`，用来对外公开一个服务（比如 `ctx.tools`、`ctx.llm`、`ctx.sessions`）。

有个细节很反直觉：`cordis.yml` 里列出的插件项是**并发启动**的，文件里谁在前谁在后，不代表加载顺序。真正决定谁先谁后的，是下一节要讲的服务依赖。

整个 dsh 应用本身就是这么拼出来的：`packages/bundle/base/cordis.patch.yml` 是一份很长的插件组合清单，部署时再用一份 overlay 配置给它打补丁、增删插件。你日常改的"加个工具""换个模型"，本质上都是在改这份清单，而不是改启动代码。

## 二、顺序由依赖决定，不是由列表决定

你一定写过这样的程序：启动时先初始化 A，再初始化 B，因为 B 要用 A 的结果。

Cordis 不要求你手写这个启动序列。它的做法是：每个插件用 `inject` 声明自己依赖哪些服务，比如"我需要 `ctx.tools`"。Loader 拿到这份声明后，会**等它依赖的服务就绪了，才调用这个插件的 `apply`**。

这就是为什么上一篇里那些插件能安心地在 `apply` 里直接用 `ctx.tools.register(...)`——它执行到这一行时，`ctx.tools` 保证已经存在。

插件找不到自己需要的服务时，不会立刻报错，而是进入一个等待状态（下一节讲的 PENDING）。这也是"为什么我的插件写了却没输出"最常见的原因：它卡在等一个永远不会出现的服务。

举个实际的加载顺序：注册工具集的插件先跑，因为它对外提供 `ctx.tools`；读日志的插件等 `ctx.sessions`；跑模型的插件等 `ctx.llm`。你不需要在任何地方写"先加载 tools 再加载 agent"，依赖关系自己会把拓扑排序算出来。

## 三、fiber：每个插件的一生

每个被加载的插件实例，Cordis 都会给它配一个运行时句柄，叫 **fiber**，并在一个状态机里流转：

```
PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED
                 ↘ FAILED
```

- **PENDING**：声明过了，但需要的服务还没齐。
- **LOADING**：`apply` 函数正在跑。
- **ACTIVE**：加载完成，正常服役。
- **UNLOADING / DISPOSED**：正在拆除，或已经拆干净。
- **FAILED**：`apply` 抛异常了。

这套状态机存在的意义，是让"卸载"这件事和"加载"一样一等公民。dsh 支持热重载——改了配置、换了插件，不用重启整个进程。能做到这一点的前提，就是每个插件都知道自己该在什么时候被回收。

## 四、注册是可以撤销的，这是关键

普通插件框架最容易写崩的地方，就是卸载：监听器忘了摘、定时器忘了停、连接忘了关。

Cordis 的约定是：**你在 `apply` 里做的一切注册，都应该在卸载时被自动撤销。**

好消息是，Cordis 内置的注册 API 本身就是"可撤销"的：

- `ctx.on(event, listener)`：插件卸载时监听器自动移除。
- `ctx.plugin(child)`：子插件随父插件一起 dispose。
- 注册服务、注册工具（`ctx.tools.register(...)`）这些 harness 自己的注册表，也会把返回的清理函数挂到调用它的插件上。

坏消息是，Cordis 管不到的资源（一个 `setInterval`、一个数据库连接、一个文件 watcher），需要你自己包一层：

```ts
ctx.effect(() => {
  const timer = setInterval(() => console.log('tick'), 200)
  return () => clearInterval(timer)   // 这就是 disposer
})
```

`effect` 的主体在加载时跑，返回的那个清理函数在卸载时跑。多个清理函数按注册的**逆序**执行——先注册的后拆，像剥洋葱。如果拆除必须有先后顺序（比如先关连接再释放池），就把它们写进同一个 disposer 里，依次 await。

还有一点：如果你在代码里手动 `ctx.plugin(child)` 挂了一个子插件，会拿到一个 fiber 句柄。`fiber.dispose()` 会等这个插件自己的所有清理函数跑完，再递归地拆掉它挂的所有子插件，包括异步的。也就是说，你拆掉一个插件时，它带出来的一整棵插件树都会被干净地收走，不会留半截。

## 五、事件分发的五种姿势

上一篇讲瀑布事件时，我们说 listener 必须调 `next()` 才能往下传。这其实只是 Cordis 五种分发模式里的一种：

| 模式 | 会等异步完成吗 | 顺序 | 有没有返回值 | 典型用途 |
|---|---|---|---|---|
| `emit` | 不等 | 按注册顺序观察 | 无 | 广播，"通知一下" |
| `waterfall` | 不等 | 按顺序包装，可调 next | 有 | 中间件、改请求 |
| `parallel` | 等 | 并行扇出 | 无 | 所有人同时收到 |
| `serial` | 等 | 按顺序执行完 | 有 | `agent/turn-stopping` 终态检查 |
| `bail` | 不等 | 到第一个返回值为止 | 有 | 谁先给出决定就听谁的 |

dsh 里每个事件的模式是写死的、公开约定的。你在源码里看到一个事件名，就能立刻知道：它是广播给大家听的、是可以改请求的、还是谁先答就算数的。这种确定性，正是"一切皆插件"还能不乱套的原因——每个插件都知道自己在事件里扮演什么角色。

举两个具体对照：UI 层想实时看到模型的 chunk，订阅的是 `agent/assistant-stream`，它用 `emit`，监听器只读不改，谁都不挡谁；而 `agent/pre-step` 用 `waterfall`，内容安全插件、压缩插件、你自己加的 hook 排成一条链，每个都能改消息、也能选择拒绝。同样是"插件被通知"，一个是旁观者，一个是决策者，差别全在事件声明的模式里。
