# 第08篇：模型层，挂三家模型主循环为什么不用改

前面几篇我们反复说"换模型不用改主循环"。但你肯定有个疑问：DeepSeek 的请求格式、豆包的请求格式、本地 Ollama 的请求格式，字段名都不一样，主循环怎么可能不感知？

答案是：它真的不感知。主循环只会说一句"我要流式输出"，背后的协议差异全被一个叫 `ctx.llm` 的翻译中间件吃掉了。这一篇就看这个中间件怎么工作。材料来自上游 `packages/llm/llm/README.zh.md`、`llm-deepseek/README.zh.md` 和 `llm-retry/README.zh.md`。

## 一、通用词汇 + 适配器：翻译发生在边界

`ctx.llm` 服务本身**不包含任何具体模型的协议代码**。它只定义三件事：

1. **规范消息长什么样**：role、content blocks、tool calls、tool results。
2. **流式分片长什么样**：block-start、text-delta、usage、finish。
3. **怎么注册一个 provider 适配器**。

适配器（`llm-deepseek`、`llm-pi-ai`、`llm-replay`）负责把这套通用词汇翻译成具体 API 的 HTTP 请求，再把响应流翻译回通用分片。主循环看到的永远是通用分片，它不知道身后是 Anthropic Messages 协议、OpenAI Chat Completions、还是录好的回放脚本。

这就是第04篇讲的 seam 的标准玩法：Definition 是通用词汇，Provider 是协议适配器，Consumer 是 agent-loop、会话标题生成器、compaction 摘要器。这三个 consumer 从来没写过一行"如果是 DeepSeek 就这么拼请求"。

举个实际例子：DeepSeek 官方适配器的 baseURL 居然是 `https://api.deepseek.com/anthropic`——它直接走 Anthropic 的 Messages 协议。但主循环根本不知道这件事，对它来说那就是个普通的 `provider: 'deepseek-official'` 路由。

## 二、请求是深度冻结的，谁也不能半路改

一个很关键的设计：**agent-loop 构建出来的请求，在到达适配器之前是深度冻结（deeply frozen）的**。

这意味着两件事：

- 监听器（包括那些想加 hook、改 prompt、加系统消息的插件）只能读，不能改。
- 适配器只能做协议翻译，不能偷偷改消息内容。

为什么要这么死？因为请求是会话日志的纯函数——它必须能从 JSONL 日志重放出来。如果允许中间某个插件偷偷改请求，那重放出来的请求和当时真实发出的就不一致了，审计、回放、测试全部失效。

你想在请求里加东西？dsh 给你留了一个口子：`configureCall(config, signal, configure?)` 这个纯函数钩子，在请求冻结之前介入，显式选择控制项（比如"用最低推理强度"、"把 maxTokens 设成多少"）。这是合法的"改请求"——它发生在冻结之前，而且是显式的、可记录的。冻结之后再想动，门都没有。

## 三、失败按 code 路由，不看消息文本

模型调用会失败。dsh 的做法很工程化：**所有失败都带一个稳定的错误 code**，消费方按 code 写分支，不去解析错误消息的人类语言。

常见 code 包括：

- `NO_ADAPTER`：这个 provider 没注册。
- `MISSING_CREDENTIAL` / `INVALID_CREDENTIAL`：没配 key 或 key 格式错。
- `AUTH`：401 鉴权失败。
- `RATE_LIMIT`：限流。
- `CONTEXT_WINDOW_EXCEEDED`：上下文超长（触发第06篇讲的压缩恢复）。
- `QUOTA` / `ACCOUNT_QUOTA`：额度耗尽或账号余额不足。

消费方代码长这样："如果 code 是 RATE_LIMIT，等一下重试；如果是 CONTEXT_WINDOW_EXCEEDED，触发压缩；如果是 AUTH，提示用户去登录。"没有任何地方写"如果消息里出现 'rate limit' 字样"。这是工业级系统和 demo 的差别——错误信息会变，code 不会。

还有一个细节：凭据本身也按 seam 管。`resolveAuth()` 在每次请求开始时才去取当前配置里的凭据，不是启动时读一次就缓存。你在 UI 里换了 key，下一个请求自动用新 key；正在跑的请求保留老 key。这样你不用重启应用就能换模型供应商。

## 四、重试是外挂，stream() 本身只试一次

这里有个反直觉的设计：`ctx.llm.stream()` **永远只尝试一次**。失败就失败，流以一个 error finish 结束，不会自己重发。

重试是另一个插件 `dsh-llm-retry` 在做，而且它不是在网络层重试，是在 **agent step 边界**重试。也就是说：一次模型请求失败了，整个 step 在会话日志里被标记为"待重试"，然后从这一步开始重跑。为什么要这么设计？因为模型请求是持久化的——你重试一次，就要在日志里记一次新的 attempt，不能偷偷在网络层重发然后装作什么都没发生。

重试策略分两档：

- **normal mode（默认）**：只对 `RATE_LIMIT`、`SERVER`、`TIMEOUT`、`TRANSPORT`、`EMPTY_RESPONSE` 这几类瞬时错误重试，最多 5 次，退避从 500ms 到 10s 带抖动。
- **always mode**：无重试上限，一直试到成功、取消或插件卸载。适合后台长任务，但每次重试都真的花钱调 API。

注意：直接调 `ctx.llm.stream()` 的辅助请求（比如生成会话标题、做 compaction 摘要）不走重试——它们是一次性的，重跑由调用方自己决定。

## 五、模型元数据：每个模型自己报家底

最后一件事：适配器注册时会公布这个模型的"家底"，主循环拿到后才能做正确决策：

- **contextWindow**：上下文窗口多大（DeepSeek V4 是 1,048,576 token）。
- **maxTokens**：单次输出上限。
- **reasoningEfforts**：支持哪几档推理强度（off / low / high / max）。
- **inputModalities**：能不能吃图片。
- **systemPromptUpdate**：系统提示词怎么更新——是只能改开头那条，还是可以在对话历史里任意位置插新 system（`in-history` 模式）。

最后这条很有意思。有些模型只读对话开头那条 system message，你想中途改提示词它根本不理；有些模型支持在历史里任何位置插新 system，模型读到最新的那条就生效。dsh 把这个能力暴露成一个字段，agent-loop 自己决定怎么写历史——它不需要为每个模型写 if/else。

配置也有个细节：适配器的配置改了，**下一个请求生效，正在跑的请求保留原配置**。这是工业系统的基本素养——你不能改着改着把正在进行的请求搞坏。

还有个叫 `purpose` 的元数据：主对话请求不带 purpose；辅助请求（生成会话标题、做 compaction 摘要）会声明自己的 purpose，作为不可见的传输元数据带给适配器。适配器知道"这次请求是后台任务，不是用户在等回复"，可以据此选更便宜的模型、更短的超时。但模型本身看不到 purpose，它影响不了 prompt。
