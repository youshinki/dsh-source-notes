# 第10篇：工具是怎么被模型看见的，注册到可见之间有两次投影

第05篇讲了一个工具被调用之后会发生什么。这一篇反过来，讲**调用之前**：你写了一个工具函数，模型怎么会知道有这么个东西、知道它要什么参数、知道什么时候该用它。

答案不是"把函数名塞给模型"。从你注册那一刻到模型真正看到，中间有两次投影，每一层都在砍东西。

材料来自上游 `packages/core/tools/README.zh.md`、`packages/mcp/mcp-client/README.zh.md` 和 `packages/core/tool-executor-ptc/README.zh.md`。

## 一、第一次投影：定义里有一半是给引擎看的

写工具用的是 `defineTool`，不是裸函数。这个包装的意义在于——它要求你把**模型的视角**和**引擎的视角**分开填：

```ts
ctx.tools.register(defineTool({
  name: 'read_file',
  description: 'Read a file from disk.',
  parameters: {
    path: { type: 'string', required: true, description: 'Absolute file path' },
    limit: { type: 'number' },
  },
  output: { schema: { type: 'string' }, render: (_a, v) => [{ type: 'text', text: v }] },
  async execute(args, exec) { /* ... */ },
}))
```

这里有几个字段是**永远不会发到协议层**的：`execute` 函数、`output.schema`、`render`、`finalizeContent`、`timeoutMs`、各种呈现回调。

模型那边只收到三样：`name`、`description`、`parameters` 的 schema。这就是第一次投影——**注册表持有一个丰富的类型化定义，投影出去的是一个瘦 schema**。

为什么要砍得这么狠？因为模型看到的每个 token 都在花钱，而且都在占用上下文。`output.schema` 对引擎是必需的（它要校验返回值、要渲染卡片），但对模型毫无用处——模型不需要知道返回值 JSON 的形状，它读的是渲染后的文本。

反过来，`parameters` 那一层被完整保留，因为模型必须知道怎么填。而且这套 schema 不是手写 JSON Schema，是一个统一 DSL：`string / number / integer / boolean / array / object / oneOf`，外加只在作者侧使用的 `json`。它编译出一个精确的 TypeScript 类型给 `execute` 用——**模型看的是 schema，你写代码时看到的是类型**。

## 二、第二次投影：不看注册表，看"这一步谁能上场"

这是 dsh 里最容易被忽略、也最容易踩坑的一层。

工具注册了不等于模型能看到。每个模型步骤开始前，执行器会拿到一份 `ResolvedToolSet`——**这一步专属的可见工具集合**。它是从注册表算出来的，算法里叠了三层过滤：

**第一层，`when` 条件**。注册时可以带一个条件函数，它收到 `{ agent, modelSelection, signal }`，每个步骤算一次。返回 false，这个工具就从描述、PTC 绑定、执行集合里全被排除。

判断依据可以是"当前选的是哪个模型"——比如某个工具只有强模型才该用。也可以是"当前 agent 是什么角色"。注意条件抛异常不是"当它不存在"，而是直接以 `TOOL_ACTIVATION_FAILED` 中止步骤准备——因为一个算不明白的条件说明状态已经坏了，不能装作没事。

**第二层，`restrict`**。按 agent 加允许/拒绝掩码，多个掩码取交集。这一层的作用是"这个子 agent 不许用 bash"，而不是"这个工具不存在"。

**第三层，作用域**。每份集合只准入原 agent 作用域里的原注册，跨作用域的不会漏进来。

三层算完，得到的集合会同时传给两处：提示词组装（决定描述里列哪些工具）和这一次 `ctx.tools.execute()` 的批次。**两处必须是同一个集合**，否则模型会看到描述里有的工具、调用时却报 `UNKNOWN_TOOL`。

批次结束就释放，同一步骤内重试复用同一份。这个设计有个好处：限制变了、工具被注销了、同名被替换了，都只影响"还没开始的调用"，已经跑起来的不受影响。

## 三、MCP 是怎么混进来的：它没有特权

外部 MCP 服务器的工具，进来的时候走的完全是原生那条路——`ctx.tools.register()`，用服务器给的 schema。

不同的是命名：`mcp__<serverName>__<rawName>`，比如 `mcp__github__create_issue`。这个前缀不是装饰，是**冲突解决的机制**：

- 两个服务器都有 `search`？没问题，`mcp__github__search` 和 `mcp__web__search` 并存。
- 两条配置用了同一个 serverName？后加载的那条直接报错，不允许模糊。
- 服务器在一次列表里重复报同一个工具名？整个列表按无效拒绝，保留上一组。
- 工具更新时跟已有名字冲突？整次更新被拒——**绝不会给你半个工具集**。

注意最后两条的共同点：宁可整批不要，也不接受一个自相矛盾的注册结果。因为工具集是模型判断的依据，一半新一半旧比全旧更危险。

还有个影响很深的设计：名字只要不变，**会话历史和权限规则跨重启依然有效**。你昨天批准过的"允许调用 mcp__github__create_issue"，今天重启后还是同一条规则。名字变了，这些全废。

连接管理也是工业式的：断开后 500ms 起翻倍退避、上限 30s、连续 10 次失败就把这个服务器的工具摘掉并停止重连，但**在断线期间旧工具仍然列着、调用会失败**。为什么保留？因为悄悄从列表里消失会让模型以为工具没了，去尝试别的路径；明确失败才能让它知道"现在连不上"。

## 四、两种执行器：一个直接给工具，一个给 SDK

同一套工具注册表，可以配两种执行器，模型看到的东西完全不同。

**原生执行器**：把工具直接暴露成 function calling。模型一次调一个，或者一个批次里并行调多个。

**PTC 执行器**：只暴露一个工具 `run_code`，外加一份**由当前可见工具集生成的 SDK**。模型写一段代码，在代码里调用这些工具。

这个差别不只是体验，是能力边界。原生模式下，"调 20 个文件读一遍再汇总"需要 20 次往返，每次都要把结果塞回上下文；PTC 模式下模型写一个循环，中间结果留在程序变量里，不落地到对话。代价是它要管配额：每个 `run_code` 的子调用总数按 `floor(timeoutMs / 60000 × maxSubCallsPerMinute)` 算，默认两分钟超时、每分钟 1024 次，也就是 2048 次。超额不是"这次调用失败"，而是**整个程序被取消**——和超时一样的处理。捕获异常也救不回来，程序状态直接丢弃，已完成的工具操作照样生效。

这里有个细节值得注意：SDK 是由**限制后的工具集**生成的。你给这个 agent 禁了 bash，生成的 SDK 里就没有 bash 函数——不是运行时报错，是压根没有这个入口。

## 五、最后：模型看到的是描述，人看到的是卡片

工具还能带两个纯函数：`presentCall()` 和 `presentResult()`，给 Host 本地消费方用。但内置 Web 端并不直接吃这两个值，它走的是 `tool.call.toolview` 选 renderer，从原始参数、结果内容、失败状态和 metadata 里派生卡片 props。

也就是说，**"模型看到的"和"人看到的"是两套完全独立的投影**：模型看 schema 和文本结果，人看卡片和摘要。同一个工具定义，喂给两个不同的消费方，各自只取自己要的那部分。
