# 第09篇：插件三层结构，一个仓库怎么长出五个形态

前面几篇基本都在讲"一个插件内部怎么干活"。但你可能有个更实际的问题：dsh 有桌面版、Web 版、命令行一次性任务版、ACP 协议版、SDK 版，这五个形态是不是五套代码？

不是。它们共用同一套插件，差别只在——**配置叠了几层 patch**。

这一篇讲清这个叠法。材料来自上游 `packages/bundle/README.zh.md`、`packages/boot/app-boot/README.zh.md`，以及 `packages/bundle/base/cordis.patch.yml` 这份 548 行的清单本身。

## 一、plugin 是行，bundle 是补丁，profile 是结果

先分清三个词，dsh 里它们是不同层级的东西：

**plugin**：一个 npm 包，导出 `apply(ctx)`，在 Cordis 里被挂载成一个运行时实例。这是第03篇讲的东西。

**bundle**（组合包）：不是插件，是一份 `cordis.patch.yml`。它自己一行代码都不跑，只负责"往配置里塞哪些行、改哪些行的配置"。每个组合包在自己的 `package.json` 里用一个字段声明它：

```json
{"dsh": {"bundle": {"patch": "./cordis.patch.yml"}}}
```

**profile**：真正被启动的东西。它在 `$DSH_HOME/profiles/<name>` 下，由"若干个组合包的 patch 叠加 + 自己的一份 `cordis.patch.yml`"组成。dsh 用 `--profile` 指定启动哪个：`web`、`headless`、`acp`、`sdk`、`sdk-minimal`。

所以"五个形态"的真相是：五个 profile，四份叠法不同的 patch，一套插件。

## 二、叠法：base 打底，模式层覆盖，用户层收尾

`bundle/base` 是所有 profile 的共同底座。它那份 patch 只有**一个 insert**——往空的 profile 根里一次性插入几百行插件：

```yaml
- insert:
    - id: llm
      name: '@deepseek-ai/dsh-llm'
    - id: session
      name: '@deepseek-ai/dsh-session'
    - id: hmr
      name: '@deepseek-ai/dsh-hmr'
      disabled: !!js "!ctx.get('profileContext')"
```

注意每行都有个 `id`。**这个 id 就是后面所有覆盖操作的锚点**。base 里 `llm` 这行叫 `llm`，模式层想改它的配置，就写 `- id: llm` 加新 config，不用重复写包名。

然后 `web-app` 在 base 之上再叠一层，只管 Web 特有的东西：挂 `webserver`、`web-runtime`、`connection`、浏览器端那一串 client 行。`headless` 则相反，它在注释里写得很直接——"**不挂 Host、不挂 HTTP server、不挂 Web runtime、不挂任何浏览器插件**"，只挂一个 `headless-runner` 和一个读命令行参数的 startup provider。

最后是你自己的那份 `cordis.patch.yml`，位于 harness home。规则是**先应用逐 profile 的文件，再应用 home 级文件**，所以后者优先级更高——你在 home 级写的覆盖，能盖掉 profile 自己的。

官方 base 那份 patch 开头有一段注释，把设计约束说得很清楚：一行配置如果随模式不同而不同，就**不要放在 base**，要放到各个模式 bundle 里去。这样保证"任何一行最多只被一个 bundle 层 + 用户层碰过"。这是个很克制的分层原则——它防的不是写错，而是"这行的值到底谁说了算"说不清。

五个 profile 里有个例外：`sdk-minimal` **不用 base**，自己带一整棵完整的 patch 树。它的定位是不需要 Web、不需要 Host 的极简 SDK 嵌入场景——如果还从 base 叠一个几百行的底座再删，反而不如直接给一份干净的。这也说明"分层"不是教条，是能省事才分层。

你日常改的东西，绝大多数落在最上面那层。想加个工具？写一段 `insert`。想换个模型？找到 `llm` 那一行改配置。想关掉遥测？找到那行写 `disabled: true`。这些都不需要改启动代码，也不需要重新构建——配置文件的事，配置文件解决。

## 三、patch 的语义：整行替换，不是深度合并

这是最容易踩坑的地方。dsh 的 patch 对某一行做覆盖时，**替换的是整份 `config`，不是往里面 merge**。

所以模式层想改 base 某行的某一个字段，必须把这一行所有字段**重述一遍**，包括它不打算改的那些：

```yaml
- id: session-query-sqlite
  config:
    path: ':memory:'
    openAt: never
```

这里 `path` 可能 base 里已经有了，但它照样要写。代码注释里反复强调这件事，因为一旦你只写想改的那个字段，剩下的字段就全丢了。

为什么不做深度合并？因为深度合并的语义太暧昧：数组是替换还是追加？`null` 是删掉还是设成 null？嵌套对象合并到第几层？每个框架都得自己定义一套规则然后被用户骂。dsh 选了最笨也最不会歧义的方式：整行给你，你自己写全。代价是啰嗦，收益是"配置文件看一遍就知道最终值是什么"。

## 四、`!!js` 表达式：配置里的值是延迟算出来的

上面那些 yaml 里有不少 `!!js`，比如：

```yaml
disabled: !!js "!ctx.get('profileContext')"
task: !!js ctx.headlessStartup.task
```

这不是模板字符串，是 Cordis 在加载配置时**求值的表达式**。它带来的能力是：配置项的值可以依赖运行时的 ctx——某个服务在不在、某个 provider 提供了什么、命令行参数是什么。

所以"禁用某行"不是写死 `true`，而是写"**如果没有 profileContext 就禁用**"。这意味着同一份 base patch，在桌面版（有 profile 上下文）和别的场景下会自动产生不同结果——不用维护两套配置。

`headless` 那份更妙：`task: !!js ctx.headlessStartup.task`，任务内容从哪来？从命令行位置参数来。startup provider 先把它解析好、注册成服务，然后 `headless-runner` 这一行才去读。这就是为什么它要给 runner 写 `inject: [headlessStartup]`——**告诉 Loader"等这个服务就绪了再挂我"**，也就是第03篇讲的依赖拓扑排序，在配置文件层面显式用上了。

## 五、失败了怎么办：跳过、警告、还是整个不启动

几百行插件，总有一行会挂。dsh 的处理分三档：

**第一档，普通行失败**：产生一条带标签的 warning，启动继续。所有能起来的插件都会起来。

**第二档，required 行失败**：整个应用拆掉，非零码退出。全局 required 列表覆盖的是那些缺了就完全没法用的东西——`agent-loop`、`tool-executor-native`、`tool-executor-ptc`、`webserver`、`web-runtime`、`modules`、`connection`。少任何一个，这个形态就不是它了。

**第三档，组合包本身有问题**：比如它的 `package.json` 里的 DSH 版本要求跟当前运行时对不上，或者平台声明不匹配（`dsh.bundle.platforms: ["darwin"]` 在 Linux 上就跳过）。这种不是报错退出，而是**整个这一层 patch 被跳过**，记到 `skippedBundles` 里，每次启动报告一次，其余层照常生效。

第三档的设计意图很明确：组合包是可以从外部安装的（`dsh plugin --profile <name> add <package>`），装了个不兼容的包不应该让你的编辑器打不开。跳过它、告诉你、继续跑。

还有个细节：版本兼容检查发生在**导入插件模块之前**。被拒绝的插件永远不会被 import，所以它那些顶层副作用一行都不会跑。这是个安全边界，虽然文档也老实承认"这不是防范恶意包代码的沙箱"。

---

串一下：第03篇讲插件怎么被 Cordis 装上拆下，这篇讲的是**谁决定装哪些插件**——一份可以层层叠加的 patch 清单；第04篇讲 seam 让能力可替换，这篇讲的是让"整个应用形态"可替换的机制，粒度更大一层。

这里也能看出 dsh 的一个整体思路：它能替换的东西，从"一个模型供应商"（第08篇）、到"一个工具"、到"一整套应用界面"，走的是同一套机制——**声明、注册、按 id 覆盖**。没有为"发行版"单独发明一套构建系统。
