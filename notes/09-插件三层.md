# 第09篇：插件三层结构，plugin / bundle / patch 怎么组装出一个应用

第03篇我们讲清楚了"一个插件长什么样、怎么被加载"。但那时候有个问题被跳过了：dsh 里有几百个插件，它们的清单从哪来？总不能手写一份几百行的配置文件吧。

这一篇就解决这个：dsh 用三层——plugin、bundle、patch——把"一个插件"和"一个可运行的应用"之间的那段组装工作拆开了。材料来自上游 `packages/bundle/README.zh.md`、`packages/bundle/base/cordis.patch.yml` 的注释和 `packages/boot/app-boot/README.zh.md`。

## 一、三层各管什么

先给结论：

- **plugin** 是最小单位，一个导出 `apply(ctx)` 的模块，对应一个 npm 包。它只关心"我怎么在 ctx 上注册东西"。
- **bundle** 是一份"插件组合包"，它不写代码，只声明一个 patch 文件（或一组有序的 patch 文件）。base、web-app、headless、acp-app、sdk-app、sdk-minimal 就是官方随发行版交付的六个 bundle。
- **patch** 是一份 YAML 增量层，里面只有两种动作：`insert` 新行、按 `id` 覆盖已有行。

关键点：**bundle 里没有代码，只有清单**。`packages/bundle/web-app/` 里除了一个 `cordis.patch.yml` 和一点 locale、presets、src，主体就是那份 YAML。所以"装一个 bundle"这个动作，本质是把一层配置叠到你的 profile 上，不是装一堆依赖。

而 profile 是什么？就是 `$DSH_HOME/profiles/<name>` 一个目录，内容是"可安装的组合包列表 + 自己的 `cordis.patch.yml`"。`dsh --profile web` 启动的东西，就是这个目录。

六个官方 bundle 的分工，一句话就能说清：

| bundle | 干什么 | 挂的 ctx key |
|---|---|---|
| base | 共享核心，只有 patch 没有代码 | — |
| web-app | 浏览器应用层 | 多条 Web 配置行 |
| headless | 一次性命令行任务 | `headless-runner` |
| acp-app | 编辑器/客户端协议的 stdio 应用 | ACP bridge |
| sdk-app | SDK JSON-RPC stdio | SDK 服务器 |
| sdk-minimal | 不用 base 的独立极简版 | 完整 patch 树 |

注意最后一个 `sdk-minimal` 是个特例：它不基于 base，自己提供一整套完整配置树。这反过来证明了一个设计判断——base 不是"必需的底座"，只是一个"大家都同意共享的那部分"。当你的场景小到不需要那部分时，完全可以不要。

而且 bundle 不只官方的能用。树外（out-of-tree）bundle 通过 `dsh plugin --profile <name> add <package>` 装进 profile；领域包也可以在自己的仓库里声明附加层，不必挤进 `packages/bundle/` 这个目录。也就是说，"造一个 dsh 变体"这件事，不需要 fork 主仓库。

## 二、叠加顺序：后写的赢，按行算

一个 profile 启动时，patch 层是按固定顺序叠上去的：

1. **空 profile 根**（什么都没有）
2. **base 层**：`dsh-base` bundle 的一次大 `insert`，一次性把共享核心的几十个插件插进来
3. **模式层**：web-app / headless / acp-app / sdk-app 其中一层，按 `id` 覆盖 base 里那些"这个模式要不一样"的行
4. **用户的 profile patch**
5. **home 级 patch**（比 profile 级优先）
6. **`--patch` 命令行 overlay**

规则只有一句：**按 `id` 定位，同一行后写的赢**。这是整层机制的地基。

base 的注释写得很直白："Later bundle patches and the user's profile cordis.patch.yml address these rows by id, with the last write winning per row."（后面的 bundle patch 和用户 profile patch 都按 id 定位这些行，逐行后写覆盖。）

所以你想改某个插件的配置，不需要找到它、不需要复制整段，只要在你的 profile patch 里写一行 `- id: llm` 加新 config 就完事。

## 三、replace 不是 merge，这是最容易踩的坑

接下来是最反直觉、也最容易写错的一条：**patch 覆盖一个行时，是替换整行的 `config`，不是深合并**。

base 的注释专门警告了这一点："A patch replaces the targeted row's whole `config` rather than merging into it."（patch 替换目标行的整个 config，而不是合并进去。）

这意味着：如果你只想改一个字段，也必须把这一行的**所有字段全部重述一遍**，否则没写的字段就变默认值了。

就因为这个，base 里故意不写那些"每种模式值都不一样"的行——它把这些行留给模式 bundle 去写完整版本。base 注释原话是："a row whose value differs by mode does NOT live here: it belongs to each mode bundle, keeping any single row down to one bundle layer plus the user's."（值按模式不同的行不放这里，放在各模式 bundle 里，这样任何一行最多只有一层 bundle 加用户层。）

这个设计意图很清楚：避免"base 写一半、web-app 又补一半"，最后谁也不知道这行的完整值是什么。宁可让 web-app 把整行重述一遍，也不要靠多层的局部合并拼出一个值。

看 web-app 里的实际例子：它覆盖 `session-query-sqlite` 时，把 `path` 和 `openAt` 两个字段都重新写了一遍，不是只改其中一个。

顺带一提，这条规则对"读代码"也有好处。你看到一个行被三层引用过，只要看最后一层的手里那段 YAML，就知道它最终是什么——不用像 Kubernetes 的 strategy merge patch 那样，把三层拼在脑子里算一遍。代价是写的时候啰嗦一点，收益是读的时候不用推理。这是个刻意的取舍：**宁可让写的人多写十行，也不让查问题的人多推三步**。

## 四、行里可以有表达式，而且行序不决定加载顺序

patch 里最灵活的一招是 `!!js` 表达式，启动时插值。base 里到处在用：

```yaml
- id: hmr
  name: '@deepseek-ai/dsh-hmr'
  disabled: "!!js !ctx.get('profileContext')"
```

这行的意思是：如果没有 profileContext（比如 `dsh --profile web --help` 这种只查帮助的场景），就把 hmr 禁用掉，别起一个没用的服务。

`web-app` 里还有更细的条件：

```yaml
- id: desktop-product-telemetry
  disabled: "!!js ctx.get('profileContext')?.name !== 'desktop'"
```

同一份 web-app patch，桌面版和浏览器版共用，靠这一行区分。这就是"一份清单组装出多个产品"的具体做法。

但注意一件事：**行在 YAML 里的先后顺序不决定加载顺序**。base 注释说得很清楚："Row order carries no load semantics (activation is service-availability driven); the grouping is for readers."（行序不承载加载语义，激活由服务可用性驱动，分组只是为了读者好读。）

这句话直接呼应第03篇：真正决定谁先加载的，是 `inject` 声明的服务依赖，不是配置文件里的行号。所以那份几百行的 patch 文件，作者可以按"工具类一组、会话类一组、Web 类一组"来排版，纯粹为了人看，不影响任何行为。

## 五、加载失败分两种：一种是跳过，一种是炸掉

最后一个工程细节：并不是所有错误都该让应用起不来。

**会跳过的**：bundle 解析失败、manifest 读不出、patch 加载失败、平台不匹配（bundle 可以用 `dsh.bundle.platforms: ["darwin"]` 声明只支持哪些平台）、版本范围不满足。这些情况下，整个层被跳过，但"你选择安装过这个 bundle"这个记录保持不变，下次还能用。跳过的 bundle 会列进 `skippedBundles`，启动器每次启动报一次。

为什么要这么宽容？因为 bundle 是可插拔的第三方东西，一个坏的第三方包不该让整个应用起不来——降级但能跑，比彻底挂掉强。

**会炸掉的**：profile 自己的 `cordis.patch.yml` 写错了、用户 patch 有错。毕竟那是你自己的配置，写错了就该明确报错，不能默默吞掉。

还有个很讲究的保护：插件被版本检查拒绝时，**它的模块永远不会被 import**。app-boot 的原文是"被拒绝的插件永远不会导入其模块"。检查发生在启动器自己那份组合上，不改 profile 文件。想给某个精确版本开豁免，写在 profile 自己的 `compatibility.json` 里——不是 `package.json`，所以开豁免不会动到依赖清单。

另外，`--dump-config` 能让你在启动前看到组合后的完整条目列表，按源文件和 patch 层分组注释，还能直接当 YAML 加载。想知道"我这一行最后到底生效成什么"，用它。

这个命令的价值常被低估。调 bundle 最痛苦的不是写错，是"我明明改了但没生效"——不知道哪一层盖住了我。dump 会把每一层标出来，还能报出"某个 patch 里的行没匹配到任何目标"这种静默失效。配置系统里，**可观测性比灵活性更重要**。

还有一个叫 `sanitizeProfile` 的恢复函数，值得单独提一句：当 profile 因为 patch 写坏了彻底起不来时，它会把你那份 `cordis.patch.yml` 改名成带时间戳的 `.bak` 备份（不删），然后把 bundle 列表恢复成调用方指定的状态。注意它只备份、不删除，也只在下次启动时重新创建一个空 patch。为的是同一个原则——**自动修复可以，自动销毁不行**。

---

串一下：第03篇讲 Cordis 怎么加载一个插件，这篇讲这些插件清单从哪来、怎么叠出来的。第04篇说一切皆 seam，那 bundle 就是"一次性把一堆 seam 的 provider 和 consumer 都挂上"的清单。第08篇说模型层可替换，落到配置上就是"改 `- id: llm` 那一行"。

三层的分工可以一句话收尾：**plugin 管能力，bundle 管组合，patch 管差异**。你要给这个系统加个新能力，写个 plugin；你要造一个新的产品形态，加个 bundle；你要在自己的机器上微调，改 patch。三者互不越界。
