# 第05篇：工具流水线，模型说要跑 bash 时到底发生了什么

上一篇讲了 seam：模型不知道身后是 DeepSeek 还是回放器，工具不知道脚下是本机还是沙箱。

那问题就来了：模型说一句"我要跑 `rm -rf build`"，从这句话到命令真的被执行，中间到底发生了什么？是直接跑？还是先有人审一遍？审不过怎么办？

答案是：**这条路径上有三段瀑布、两道闸、一次可能的弹窗审批**。工具作者只写中间那段真正干活的代码，前后全由流水线插进来。材料来自上游 `docs/tool-execution-pipeline.zh.md`。

## 一、先看全景：一条线串起来

模型吐出的 assistant message 里带了 tool-call block，harness 把它交给一个 ToolExecutor。从这一刻起，事件顺序大致是这样：

1. 落一条 `tool/call` 事件（**执行前就写进 JSONL**，所以中断了也知道模型当时要干嘛）。
2. UI 弹一张"待执行卡片"，调 `presentCall(args)`。
3. 进 `tools/pre-execute` 瀑布：hooks、权限策略、沙箱检查都排在这里。
4. 单调守卫（monotonic guards）投票：allow / abstain / deny。
5. 如果需要用户确认，弹 `ctx.approval` 一次性问询；没人应就算拒。
6. 进 `tools/execute` 瀑布：超时、重试、指标采集都是"包一层"的角色。
7. 真正的工具函数 `execute()` 才跑。
8. 如果是文件写入类工具，先过 `fs/write-intent` / `fs/edit-intent` 这道门。
9. 工具自己发的内部事件（`todo/write`、`fs/observed`、`hook/invoked` 等）此时落盘。
10. 进 `tools/post-execute` 瀑布：accept、block、replace、追加上下文都在这一段。
11. 归一化：抛异常变成 `isError` 结果，不让异常崩穿。
12. `ToolDefinition.finalizeContent` 跑最后一道纯内容不变式。
13. `tools/result` 同步广播，落 `tool/result` 事件（**模型真正看到的那一份**）。
14. UI 把待执行卡片换成完成卡片。
15. 整批 tool call 都结算完，再把 `additionalContexts` 里的额外说明按 FIFO 喂回模型。

注意三段瀑布（pre/execute/post）都是第03篇讲的 Cordis 瀑布事件——**每个 listener 都能改这次调用**。这就是 dsh 工具系统能"插件化"的根本原因：工具作者只写自己的 `execute()`，策略、审批、沙箱、超时、结果改写全是插在瀑布里的独立插件。

## 二、pre-execute：到底是谁在拦

pre 瀑布是策略层的主战场。dsh 把这里的玩家分成两类，顺序很关键。

**第一类是普通 listener**：内容安全、命令审计、日志、hook 脚本，谁都能注册一个 `tools/pre-execute` 监听，看一眼要跑什么。它可以直接改 args（比如把相对路径补成绝对路径），也可以调 next 往下传。

**第二类是单调守卫（monotonic guards）**：它的特殊性在于"单调"——一旦某个守卫投了 deny，后续任何守卫都不能把它翻回 allow。这是个很重要的设计：你不希望"最严的策略说不许，后面一个宽松插件就放行了"。守卫之间是取最严交集，不是互相投票。守卫自己的身份信息是被保护的，不能被 listener 看到或伪造。

**第三道是审批弹窗**：pre 里某个 listener 觉得"这条命令得问一下用户"，就会发起 `ctx.approval` 一次性问询。用户点允许，这次调用继续走；点拒绝、取消，或者干脆没人响应（headless 场景），按**拒绝**处理。注意是 one-shot——允许这一次，下一次同样的命令还得再问。这就是为什么你在 dsh 里看到"要不要允许执行 rm"这种弹窗，它不是工具自己写的 UI，是 harness 内置的审批 seam。

deny 之后不是报错崩出去，而是落一条"被拒"的结果，继续走后面的 post 瀑布和 `tools/result`。模型那边看到的是"这个工具返回了一个拒绝信息"，它自己会决定下一步怎么办。

## 三、execute 瀑布：包一层，而不是改工具

execute 这一段的角色很特殊：它**不拦事，它只是围着真正的 execute() 包一层**。

- 超时：到点没返回，包一层 Promise.race。
- 重试：特定错误码自动重跑。
- 指标：记耗时、记 token、记工具名。

这些横切关注点和工具本身的业务逻辑没关系，但每个工具都需要。如果按"在每个工具里手写一遍"的做法，二十个工具就二十份重复代码。dsh 的做法是：它们全是 `tools/execute` 瀑布里的 listener，统一在真正的 `execute()` 前面包一层 wrapper。**工具作者完全感知不到这些东西存在**。

## 四、post-execute：结果还能再改一次

工具跑完了，结果不是直接喂给模型的。中间还有两道闸。

**第一道是 post 瀑布**。这里的 listener 可以做四件事：

- accept：这个结果挺好，原样放行。
- block：这个结果不该给模型看（比如命中了隐私字段），拦下来。
- replace：把结果替换掉（比如把超长日志截短）。
- add context：往这次调用后面追加一段额外说明（"刚才那条命令实际跑在沙箱里"）。

**第二道是文件系统门 `fs/write-intent` / `fs/edit-intent`**。注意它只对 `tool-fs` 这一族生效——通用 post 瀑布管不到文件写入这种需要"先读后写"的场景。具体说，dsh 的文件编辑工具会先抛一个 edit-intent 事件，把"我要改哪个文件、改成什么样"广播出去，hook 可以在这里拦。这就是为什么 dsh 改文件比你想象中啰嗦——它多走了一道意向申报。

工具自己也可以发一批"拥有的 session 事件"：`todo/write`（待办清单更新）、`fs/observed`（我看到了什么文件）、`hook/invoked`、`hook/result`、`tool/ptc-dispatch`（子调用）。这些都是业务事件，不是策略事件。

## 五、最后两道保险：归一化和 finalizeContent

结果出来之后还有两步，是为了"模型看到的东西必须稳定"。

**归一化**：任何一段瀑布里抛出来的异常——pre 抛、execute wrapper 抛、post 抛——都会被捕获，转换成一个 `isError: true` 的结果，不允许异常穿透到 agent-loop。这是为什么主循环第02篇讲起来那么干净：所有脏活在工具流水线里就被接住了。

**finalizeContent**：它是工具 Definition 自己声明的最后一道回调，跑在 post 之后、`tools/result` 广播之前。它只做一件事——**强制执行"这是纯内容、同步完成"的不变式**。它是你写插件时最后的兜底：不管前面多少 listener 加了乱七八糟的上下文，到 finalizeContent 这一步都会被收敛成一份干净、可 JSON 序列化、没有副作用的结果。`tools/result` 事件本身是不可变的、冻结的——模型看到的最终结果，就是这一刻拍下来的快照。

还有个细节叫 PTC（run_code 模式）：如果你允许模型起子进程代码执行，那些子调用也走完全一样的流水线，带着父级 token、记 `tool/ptc-dispatch` 事件，拒绝会被当成有约束力的驳回。也就是说，**主流程和子流程共用同一条流水线**，没有"内部特权通道"。
