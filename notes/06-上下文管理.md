# 第06篇：上下文管理，聊了一千轮模型还记得第一天吗

你和模型聊得最久的一次，是多少轮？

工业级 harness 跟玩具 demo 的一个关键差别，就是长会话怎么扛。聊到第 50 轮、第 200 轮，token 早就爆了——模型怎么还记得你第一条消息说的是什么？是它记性好吗？不是，是 harness 在背后偷偷做了三件事：**把会话写成可追加的日志、用一个测量服务实时算账、在快撑爆时把旧历史压成一条摘要**。

这一篇就把这三件事讲清楚。材料来自上游 `packages/core/session`、`packages/compaction/compaction-basic` 和 `docs/session-format-status.zh.md`。

## 一、会话不是内存数组，是一条追加式 JSONL

第02篇我们提过一嘴：session/event 是持久化 JSONL，agent/* 是实时内存。现在展开讲。

dsh 的会话在磁盘上就是一个文本文件，每个事件一行 JSON：`session/start`、`user/message`、`assistant/message`、`tool/call`、`tool/result`、`compaction/start`、`compaction/summary`……模型每次说一句话、每次调一次工具、每次压缩，**都是往这个文件末尾追加一行**。它从来不改前面的行。

这带来三个很实在的好处：

**可回放。** 你把这个文件喂给另一个 dsh 实例，它能一字不差地重现当时的对话。这就是为什么 dsh 敢做"历史会话"——不是把内存状态保存下来，是把事件流重放一遍。

**崩溃安全。** 写到一半进程被 kill 了？最多丢最后那一行没 flush 的事件，前面的都在。不需要事务日志，不需要数据库，追加写本身就是最朴素的 WAL。

**压缩可审计。** 压缩做了什么决定，也以事件形式写进日志。你事后翻日志能看到：几点几分压掉了哪一段、生成了什么摘要。这跟"把内存里某段历史悄悄删掉"完全是两码事。

## 二、SESSION_FORMAT_VERSION = 4：格式是有版本号的

你可能会想：JSONL 不就是 JSON 吗，还要什么版本？

要。dsh 当前写入器版本是 `SESSION_FORMAT_VERSION = 4`，已发布基线锁定在 `dsh-v0.2.0-rc.2`。这个数字存在的意义是：**旧版本的 dsh 必须能读新版本写出来的日志，除非真的做了破坏性变更**。

上游把变更分两类：

- **同版本演进（same-version）**：加可选字段、加新事件类型、把必选改成可选。旧读取器安全地忽略它不认识的字段，新版本照样能读。这种情况不用升版本号。
- **必须升版本（version-bump）**：改已有字段类型、删字段、改事件头。这种情况老读取器会读不懂，必须升一个整数版本，并写一段"从 v3 到 v4 怎么转"的迁移代码。

这套规则听起来很学院派，但它在工程上是硬约束：你昨天生成的会话文件，今天升级 dsh 之后打开不能坏。你在 GitHub 上翻 `docs/persistence-changes/` 目录，能看到从 2026-09-11 开始每一次格式变更的完整记录——哪天加了 working-directory 字段、哪天把图片挪到离线存储，每条都有评审、有 schema 快照。

## 三、tokenMeter：一个测量服务，为每个决策定价

压缩不是拍脑袋说"看起来长了就压"，它要算账。

dsh 有个单例服务叫 `ctx.tokenMeter`。它做的事很朴素：**给定一份历史，告诉我现在已经用了多少 token、还剩多少**。但它算得很细：

- 它在同一份已提交日志 revision 上测量，不能拿"内存里可能还没落盘的草稿"来算。
- 路由到不同模型时，按那个模型的 tokenizer 定价（不同模型分词不一样）。
- 图片要单独算钱——provider 声明每张图多少 token，meter 累加到历史里。
- 切模型时（比如从大窗口模型切到小窗口），按新模型的容量重新测一遍压力，不够就先压。

压缩策略所有的数字都来自这个服务：要不要压、压哪一段、压完剩多少，全是 tokenMeter 报出来的。这是第04篇讲的 seam 的又一个实例——测量是一个可替换的缝，将来换本地 tokenizer 或者调云端定价接口，都不影响压缩逻辑本身。

## 四、四种触发方式：自动、溢出、手动、修剪

挂载 `dsh-compaction-basic` 之后，你会得到四种压缩行为：

**1. 自动压力触发。** 默认阈值是 `floor(min(W × 0.8, W − O − 65536))`，其中 W 是模型上下文窗口、O 是这次请求预留的输出 token、65536 是额外余量。到了这个水位就自动压。

**2. 溢出恢复。** 模型返回"上下文超长"错误？不是直接报错给用户，而是自动压一次再重试这个请求。默认最多重试一次。这是为什么你用 dsh 聊很久也很少看到真的 context length exceeded。

**3. 手动 `/compact`。** 在聊天里敲 `/compact` 立刻压一次。agent 正在跑的时候会告诉你"现在不能压"，你发的话会排队等压完再开始。

**4. 先修剪工具输出。** 挂 `dsh-compaction-tool-result-pruner` 之后，压缩前先把超大工具输出（比如一个命令打印了几万行日志）截短。修剪不调模型，如果修剪完就够了，连摘要都不用做——更便宜。

阈值之外还有个保留比例：默认把最近 `(W − O) × 16%` 的历史**逐字保留**，只压更早的部分。也就是说模型永远能"刚聊的话一字不差地看到"，被压成摘要的只是较早的上下文。

## 五、压缩不是删历史，是"替换一条摘要"

关键设计来了：压缩到底改了什么？

答案是：**它把一段旧历史替换成一条 `user/message` 摘要**，近期尾巴不动。具体流程是一个标记对事务：

1. 追加 `compaction/start` 事件（声明我开始压了）。
2. 调一次额外的模型请求，把最旧那段历史喂给它，让它写一段摘要。
3. 追加 `compaction/summary` 事件（写摘要内容）。
4. 在表层把被压的那段替换成这条摘要消息。
5. 追加 `compaction/end` 事件。

整个过程中，**被遮蔽的旧消息并没有从 JSONL 里删掉**。它们还在磁盘上，只是"表面视图"（也就是喂给模型看的那段对话）里不再出现了。这就是为什么 dsh 能回放——你翻日志能看到原始 50 条消息，但模型实际看到的是"摘要 + 最近 30 条"。

还有个细节很讲究：摘要那次模型请求，复用了系统提示词和工具定义的"热前缀"——也就是说，这次额外调用大部分 prompt 是已经被缓存过的，只有尾随的"请把以下历史压成摘要"和模型输出本身是新算的。这是真金白银在省钱。

压缩失败怎么办？标记对会留下一个没闭合的 `compaction/start`，作为"忙"信号，下一次请求进来会看到这个状态，不会并发压第二次。已经压成功的部分不会回滚——就像 git commit 一样，半成功也是成功。
