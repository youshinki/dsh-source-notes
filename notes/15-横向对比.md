# 第15篇：dsh、LangGraph、Claude Code，三种取舍

十四篇拆完，最后这篇换个视角：把 dsh 放到桌上，和 LangGraph、Claude Code 摆在一起看。

三家都做 agent，但它们回答的问题不一样。不搞清这个，比较就会变成"谁更强"的口水仗。

## 一、第一个差别：流程是画出来的，还是长出来的

**LangGraph 是画出来的。**

它把 agent 建模成一张有向图：节点是步骤，边是走向，状态在这张图上流动。图允许循环，所以"调工具、看结果、再决定"这种反复能表达。你想加一步，就加个节点；想加分支，就连一条条件边。

好处很直接：**流程图就是代码**。你打开代码就知道会走哪几条路，也能画给人看。要卡在中间等人确认，就在节点里 `interrupt`，图停在那儿，等人回了再继续。

**Claude Code 是包出来的。**

它给的是一套"编码场景已经调好的"agent：读文件、改代码、跑命令、搜代码这些工具都在，加一层权限规则和 hooks，你直接开用。流程不由你画，它在模型的判断里——模型决定下一步调什么。

所以它上手最快，但也最难精确控制"第几步做什么"。

**dsh 是长出来的。**

它没有一张流程图。启动时是一份插件清单，插件各自注册工具、订阅事件、声明依赖。流程是这些订阅关系叠加后涌现的——主循环走到某个时刻，谁挂了钩子谁就参与。

代价是你不能一眼看出全貌，得顺着事件名去查。好处是加能力不用改主流程：加一行清单，功能就长出来了。

想补上"看不清全貌"这块短板，它靠的是另外两样东西：事件名是公开约定的、模式是写死的（第03篇那五种分发方式），所以顺藤摸瓜能查到底；再加上配置分层（第09篇），哪一层加了什么，看清单就能对上。

## 二、第二个差别：过去能不能回去

三家都存状态，但存的东西不一样。

**LangGraph 存的是快照**：每一步执行完，把当前状态打一个 checkpoint。于是你能恢复、能回到某个 checkpoint 重跑、甚至从那儿分叉出一支新的。

**dsh 存的是事件流**：只追加，一行一件事，写完不改（第11篇）。当前状态不直接存，而是"从头推一遍"推出来的。这个设计换来的是可重放：只要日志和配置快照都在，就能把当时的请求重新算出来。

一个是"每到一站拍张照"，一个是"全程录像"。前者查起来快，后者能复盘细节。两种都能恢复，但侧重不同：快照更适合"接着干"，录像更适合"查清楚当时到底发生了什么"。

**Claude Code 介于两者之间**：会话有记录，上下文超了会压缩（把早期内容摘要掉），保证长任务能继续。它的重点不是考古，是别把窗口撑爆。

## 三、第三个差别：扩展点埋在哪

这是最容易决定"你能用它做什么"的一条。

**dsh 埋在两处**。一处是配置清单——加插件，不用改启动代码；一处是能力接口——一个"缝"后面可以换实现，比如换个模型供应商不动调用方（第04篇）。

**LangGraph 埋在图上**。加节点、加边、换节点里的函数，都是改图；图的结构本身是代码，改它就要重新部署。

**Claude Code 埋在几个事件点上**。`PreToolUse`、`PostToolUse` 这类钩子，可以在工具调用前后插自己的逻辑——比如每次提交前自动跑一遍检查。再加 MCP 接外部工具、subagent 拆子任务（还能给子任务一个独立的 worktree 隔离改动）。

三家的扩展都能用，但性质不同：dsh 是"往清单里塞"，LangGraph 是"往图上加"，Claude Code 是"往钩子上挂"。

## 四、第四个差别：边界谁来兜

这块差别很大，而且很能说明设计意图。

**dsh 是默认收紧**。出厂策略是只读，要写要显式配；权限分两道门（范围 + 时机）；没有应答者就按拒绝处理（第12篇）。

**Claude Code 是规则 + 可选沙箱**。用 allow / deny 规则声明"这类命令能跑、这类不能"，比 `.env` 这类文件直接读不了；沙箱（macOS 的 Seatbelt、Linux 的 bubblewrap）是可选开启的，开了之后写操作被限制在工作区和临时目录，读则不限。这个取舍很清楚：默认别太打扰，需要时再上锁。

**LangGraph 基本不内置**。它给你 `interrupt` 这个暂停点，权限怎么做、边界画在哪，是你的事。灵活，但也意味着你得自己设计。

## 五、所以，什么场景选哪个

说结论，不绕弯：

**流程确定、要一步步审、要能画给人看**——比如审批流、报表生成、多角色协作的业务流程——用 LangGraph。它的图就是文档，改起来心里有数。

**就是要在代码库里干活**——读代码、改代码、跑测试、提交——用 Claude Code。它把这一套调好了，你不用从零搭工具。

**要做产品底座、要长期演进、前端可能换好几茬**——用 dsh。它的分层最重，也最能扛改动：能力一份，前端多份，插件清单随便叠。

dsh 的代价也说清楚：**上手门槛最高**。你要先理解插件、seam、事件模式、清单分层，才能改对地方。它不是一个"装完就能聊"的东西，是一套"搭起来能撑很久"的骨架。

顺便说一句：这三家不是非得二选一。现实里更常见的组合是——外层用 LangGraph 编排业务流程，中间一步"让 agent 去改代码"交给 Claude Code 那类工具，底层如果想要可替换、可重放的骨架，就照 dsh 这套思路搭。

## 六、这一路拆下来，最值得抄的是什么

回头看这十五篇，我认为有三件事最值得学，跟具体框架无关：

**一是把"注册"设计成可撤销的**。能干净地拆掉，才谈得上热重载、谈得上换实现。

**二是把"请求"冻住**。发出去的请求必须能只靠日志算出来，否则一切复盘都是猜。

**三是把"出问题"默认导向拒绝**。安全设计里最贵的不是拦住坏人，是"系统自己坏了的时候别帮倒忙"。

技术会过时，这三条不会。
