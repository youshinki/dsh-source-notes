## 正文

# 第01篇：一天烧掉92万亿Token，DeepSeek Harness 凭什么扛得住 | 源码拆解系列开篇

先看一组数字。

DeepSeek Harness（下称 dsh）开发者预览版上线后，据公开报道，日活冲到 140 万，一天烧掉 92 万亿 Token。

大多数人的第一反应是：模型强。

但真去读它的仓库，你会发现答案不在这儿。dsh 的模型适配器，只是 379 个包里普普通通的一个，随时可以换掉。

它真正扛住这些数字的，是三处架构取舍。

## 一、取舍一：没有"内核"，一切皆插件

多数 Agent 框架长这样：中间一个循环，外面挂模型、挂工具、挂存储。

循环是内核，改不动，只能加钩子。

dsh 反过来了。它底下只有一个叫 Cordis 的插件框架，而 Cordis 只干两件事：加载和卸载插件，管依赖关系。

模型适配器、工具注册表、会话日志、系统提示词组装，甚至 Agent 循环本身——全是插件。

这意味着什么？换模型不是改代码，是换一个插件；不想要某个工具，卸载它，它注册的副作用会跟着撤销。

官方文档里有一句很硬的话："不存在需要打补丁的特权内核。"

好处是彻底的：任何能力都能被第三方覆盖、卸载、替换，包括官方内置的。官方甚至明确表态，系统内置的功能同样可以被第三方插件覆盖或卸载。这也解释了为什么它敢说"不用改源码就能重组整个产品"。

代价同样明显。第一，插件之间怎么协作？靠两样东西——服务（Service）和类型化事件（Event）。服务是能力接口，事件是扩展点。这部分是整套架构最难啃的骨头，第 03 篇专门拆 Cordis 的加载时序。

第二，插件一多，出问题就难定位。所以它必须配一套极强的可观测机制，也就是下面第二个取舍——这两个设计其实是互相咬合的。

## 二、取舍二：模型可见，必已记录

第二个取舍，藏在一句听起来很朴素的话里："模型可见即已记录。"

落到代码上，它对应 `packages/core/session` 这个包：一个只追加的会话事件日志。

轮次开始、步骤开始、用户消息、模型回复、工具调用、工具结果、轮次结束——所有东西都往这个日志里追加。

而模型的上下文，不是被"维护"出来的，是从这份日志里投影（`deriveMessages`）出来的。

> 配图1 放这里：仅追加日志，末端投影出模型上下文

这一手解决了三个老大难。

第一，崩溃恢复。进程挂了，重放日志就能重建现场。

第二，可观测。每次运行都有迹可循，能回放、能对比、能追责。

第三，一致性。模型看到什么，日志里就有什么，不存在"悄悄塞进去"的上下文。这条约束反过来也管住了插件：想给模型加内容，就必须先有对应的会话事件。

代价在存储和性能上：日志只增不减，必须靠压缩来治。第 05 篇专讲它怎么压缩、怎么在压缩后还能重建。

## 三、取舍三：把轮次和步骤拆开

第三个取舍是概念层的，但影响最深。

dsh 把一次交互拆成两层：**步骤（step）** 是一次模型请求加上它调用的工具；**轮次（turn）** 包含零个或多个步骤。

看着学究，实际决定了三件事。

1. **重试的粒度是步骤，不是轮次**。模型调用失败，重跑这一步就行，不用整轮重来。

2. **工具的把关、并发、结果回填，都卡在步骤边界上**。谁能执行、能并发几个、执行完怎么写回历史，边界清晰。

3. **中断可以安全发生**。在步骤之间切断，不会留下半个轮次。

轮次的边界也有明确定义：它在领取第一条输入之前打开，在不再欠任何工作时关闭。换句话说，只要有工具还没回填、有排队消息还没处理，这个轮次就不算结束。这个定义是整个调度逻辑的锚点。

完整链路简化下来是这样：

```text
turn/start
  → 领取输入
  → 组装提示词 + 工具 schema
  → agent/pre-step（可拒绝、可改写）
  → step/start
  → 冻结模型历史 → 请求模型 → 流式返回
  → 工具调用 → 前置检查 → 执行 → 后置处理
  → step/end
  → 还有欠账就继续下一步
  → turn/end
```

第 04 篇会逐行拆这条链路，包括失败步骤怎么补记缺失的工具结果。

## 四、全景图：一棵插件树

把三条拼起来，dsh 的运行时就是一棵插件树，四层。

**最底层：Cordis。** 只负责加载、卸载和依赖关系，别的什么都不管。

**第二层：core 主干。** `session`（会话日志）、`system-prompt`（提示词组装）、`tools`（工具注册表与执行流水线）、`agent`（Agent 接口）、`agent-loop`（默认驱动器）。

**第三层：能力 seam。** 模型、文件系统、shell、沙箱、子智能体、存储……每一项都由「接口定义 + 提供方 + 消费方」三件套组成，换一个提供方，整条链路就换了。

**最上层：组合包。** `dsh-base` 打底，再叠 `web-app`、`headless`、`sdk`、`acp`。

> 配图2 放这里：四层插件树

这些不是概念图。仓库里实打实有 53 个能力分组、379 个包，从 `acp` 一路排到 `workspace`。

启动时按顺序叠层：profile 里的组合包 → `cordis.patch.yml` → home patch → `--patch` 覆盖层。一条 patch 按 id 定位某个条目，直接替换它的整个配置。

所以官方那句话是字面意思：你不改源码，在配置层就能换掉任何能力。

## 五、为什么值得拆

官方文档写得很全：Cordis 教程、插件开发指南、子系统参考，都有。

如果只是复述文档，这个系列没有意义。

我要拆的是文档不写的三样东西。

1. **为什么这么设计**——每个取舍背后的代价是什么，官方选了什么、放弃了什么。

2. **边界怎么处理**——失败、取消、并发、崩溃、迁移，这些真实场景下的代码路径。

3. **换个做法会怎样**——和 LangGraph、Claude Code 放在一起比，工业级 harness 的设计分歧在哪。

而且每篇锁定一个具体提交。dsh 还在开发者预览阶段，源码会变，锁版本才能让你真正跑起来。代码和复现脚本同步在开源仓库里。

阅读门槛也说清楚：不需要你熟悉 Cordis，但最好看得懂 TypeScript，知道流（Stream）和异步取消大概是怎么回事。看不懂代码也没关系，每篇的结论和取舍分析都可以单独读。
