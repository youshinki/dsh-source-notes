# 第11篇：出了事为什么能查清楚，一份只许追加的日志

Agent 有个通病：它做错了事，你很难说清是哪一步错的。

模型说是"文件不存在"，可那个文件明明在。工具说执行成功了，可结果不对。你把对话翻了三遍，还是不知道中间发生了什么——因为大部分过程根本没留下来。

dsh 的做法很朴素：**给每一次会话装一台行车记录仪**。只往前录，不许倒带，也不许擦掉重录。这一篇讲讲这台记录仪是怎么工作的。

## 一、日志只许追加，这一条规矩撑起了所有事

先看规矩本身：会话记录是一份 JSONL 文件，一行一个事件。用户说了话、模型回了话、工具被调用、工具返回了什么、压缩发生了、子 agent 结束了——每件事都是一行。

关键在于：**写进去的行，永远不改、也不删**。

老话说得直白一点——你没法"修改历史"，只能"再补一条新记录"。比如模型先说"文件不存在"，后来发现搞错了，日志里不会把前面那句删掉，而是再记一条"更正"。

这条规矩看着死板，其实是所有能力的根。因为它等于给会话拍了一条**单向时间线**：任何时刻的状态，都是把前面所有行按顺序叠起来的产物。

## 二、能重放的真正原因：请求是从日志算出来的

很多系统说"我们有日志"，但日志只是给人看的。dsh 的日志不一样——它是**唯一的真相**。

有个很硬的约束在背后：发给模型的每一个请求，都必须能只靠这份日志重新算出来。不能依赖"当时内存里恰好有什么"，不能依赖"那天插件是哪个版本"。

打个比方：这就像照着菜谱做菜。菜谱上写着放多少盐、炖几分钟，你照着做就能复现出那盘菜。如果菜谱上写的是"放适量盐、炖一会儿"，那复现不了。

所以第08篇讲的那个"请求深度冻结"才有意义——冻结是为了保证"发出去的"和"日志里算出来的"是同一个东西。中间谁偷偷改了一笔，菜谱就废了。

## 三、光有日志还不够：配置也得一起冻住

这里有个容易被忽略的坑。

假设你昨天跑了一个会话，今天想重放它。日志有了，可是——今天的插件版本换了、某个开关被改了、模型参数调过了。你再跑一遍，结果不一样，那这次重放就没有意义。

所以重放时，dsh 会换一份配置去启动：用同级的一份配置快照，而不是当前正在用的那份。

说白了：**日志记录了"做了什么"，配置快照记录了"用什么做的"**。两样都在，才能真的回到那一天。只留一样，等于只有剧本没有演员表。

## 四、老日志还能读：因为格式会升级，而且有搬家路线

软件做久了都会遇到这个问题：格式改了，老数据怎么办？

粗暴的做法是不管了——新版本读不了旧文件，用户自己想办法。dsh 选的是另一条：每两个相邻版本之间写一条"搬家路线"，从 v0 到 v4 一路连着。

你打开一份很老的日志，它会自动识别"这是第几代"，然后沿着这条链一级一级转过来，最后变成当前格式。而且这个过程只在内存里发生，原文件不动——你的老日志还是老日志，不会被偷偷改写。

为什么这事重要？因为会话日志是有长期价值的资产。你今天踩过的坑、当时模型的反应，半年后再看，是很好的训练素材。如果每次升级都把历史废掉，那就永远只剩最近三个月。

## 五、输出太大怎么办：留首尾，全文存盘上

还有一种情况：工具返回了特别大的内容。比如抓了一个网页、读了十万行日志。这东西原样塞给模型，一次就烧掉大半上下文。

dsh 的处理是：**给模型看有界的预览，全文存到文件里**。

具体是保留开头和结尾各一段，中间省掉，然后告诉模型"省略了多少字节，全文在哪个路径，你可以用 read 或 grep 自己去取"。文字可以切，图片是整张保留或者整张省略，不会给你半张图。

为什么是首尾而不是只留开头？因为只留开头会丢掉结论，只留结尾会丢掉前提。两头都在，模型才判断得出这段输出到底有用没用。

这个设计的好处是：模型不会被撑爆，但它随时能自己去拿全文。既省了上下文，又没有丢信息。

而且这个策略跟会话记录里保存的东西是分开的——日志里记的是"渲染后的内容"，完整的规范值另有一套访问路径。所以脱敏、替换展示内容，不会顺手把程序能读到的数据也删掉。

## 六、上报是副本，不是真相

部署方一般还想把会话数据发到自己的监控系统。dsh 在这里的定位很明确：**发出去的那份是副本，本地这份才是权威**。

所以它做了两个取舍：

一是**不阻塞**。上报是排队异步做的，不会拖慢会话处理。你不能因为监控系统挂了，就让用户那边卡住。

二是**允许丢**。进程崩溃时，队列里没发出去的记录就是没了。这个取舍很实在——监控数据可以少几条，会话本身不能丢。

还有个安全细节：往外发之前可以挂脱敏规则。如果不挂，数据就原样离开进程。文档里这句话写得很直白，意思是"要不要脱敏是你的事，我们只负责给你这个位置"。

## 七、连测试都是靠重放：不用 key 也能跑

最后一个应用，挺有意思：dsh 有一套"无密钥快照测试"。

做法是：录一份真实会话，把它做成 fixture（固定样本）。以后跑测试时，不真的调模型，而是照着这份录制重放一遍。然后比对模型的可见输出和文件的实际变化，看有没有跑偏。

为什么不比对"agent 自己说的话"？因为那不可信——它说自己改好了，也可能没改。要拿证据：文件真的变了没有、终端真的输出了什么。

所以这套东西既是测试，也是回归防线。改一行动了谁，跑一遍快照就知道。
